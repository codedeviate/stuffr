stf — worked examples

Everything below runs against this build as shown. `stf <command> --help`
lists the full flag reference for any one command.


COMPRESSING A FILE

  stf pack notes.txt
      Writes notes.txt.gz beside it. The input, notes.txt, is left alone —
      unlike gzip(1), stf never deletes or replaces what you compressed.

  stf pack notes.txt -o archive.gz
      Choose the output name with -o/--output. Without it, the default is
      the input path plus the chosen format's extension (".gz" today).

  stf pack notes.txt --format gzip -o out.bin
      --format names the codec explicitly instead of inferring one from -o's
      extension. Every build — even one with no C toolchain — accepts
      gzip, zlib, deflate, bzip2, brotli, lz4, snappy, zstd and xz.

  stf pack notes.txt --format xz -o out.xz
      A default build writes xz through `lzma-rust2`, a pure-Rust port of
      Tukaani's "XZ for Java" — no C toolchain needed, and unlike zstd's
      pure fallback this is a FULL codec, not a weaker one:
      `--allow-weak-encoder` is never required for xz. Measured on a 6.5 MB
      payload against `--features c-backed`'s real `liblzma`: output sizes
      within 0.02% of each other (parity, not a discount), encoding takes
      roughly 1.2-1.3x as long, and decoding roughly 2-2.2x as long. Both
      backends select CRC64 as xz's integrity check unconditionally, and
      every position in a corruption sweep against either backend's own
      output was detected. `c-backed` is a speed choice for xz, not a
      capability one.

  stf pack notes.txt --format lzma -o out.lzma
      LZMA1, the older "alone" format xz superseded, needs `--features
      c-backed` (or `lzma-c` alone) — the default pure build has no LZMA1
      backend yet. Unlike every other codec on this page, `.lzma` defines
      NO magic bytes at all: its header's first byte encodes lc/lp/pb and
      the next four the dictionary size, not a fixed signature, so this
      format can never be detected from bytes alone, on a file or a pipe —
      see "DECOMPRESSING" below. It also has no concatenation convention
      the way gzip and xz do: unlike carrying a checksum, corruption is
      still detected almost everywhere despite that (measured at 4,166 of
      4,170 swept byte positions) through the LZMA range coder's own
      structural sensitivity, not a designed check.

  stf pack notes.txt --level 9
      --level asks the codec for a tradeoff: gzip accepts 0 (fastest,
      largest output) through 9 (slowest, smallest output). xz's range is
      the same shape, 0-9, with 6 as its default too. bzip2's range
      is 1-9, not 0-9 — it has no "store" level, so --level 0 is a usage
      error (exit 2) rather than meaning "don't compress". brotli's range is
      0-11, and unlike every other codec here its OWN default is 11 (the
      slowest setting it has), not something in the middle of the range.
      zstd's range is the widest and the only one with negative numbers —
      -131072 through 22 on this build — where negative levels are zstd's
      "fast" modes, faster than level 1 at the cost of ratio; its default is
      3. lz4 and snappy have no level at all — neither underlying crate
      exposes such a knob — so --level is accepted and silently ignored
      rather than rejected, unlike every other codec on this page.

  stf pack notes.txt --force
      Without --force, pack refuses to overwrite an existing output: exit
      code 2, the existing file left untouched, nothing written.


DECOMPRESSING

  stf unpack notes.txt.gz
      Writes notes.txt, stripping the recognised extension. As with pack,
      an existing destination is refused unless --force is given too.

  stf unpack notes.txt.gz -o out.txt --force
      Choose the name and allow overwriting an existing one.

  stf unpack data.bin --format gzip -o data.txt
      --format names the codec explicitly instead of detecting it. Some
      formats carry no magic bytes and no conventional extension, so an
      explicit --format is the only way to reach them.

  stf unpack raw.bin --format deflate -o data.txt
      Raw deflate has no header, no trailer and no conventional extension,
      so it cannot be detected at all — --format is the ONLY way in.

  stf unpack data.br --format brotli -o data.txt
      brotli defines no magic bytes at all, unlike gzip/zlib/bzip2's header
      bytes — detection from a file works only by the `.br` extension. A
      brotli stream arriving on a pipe, with no filename to go by, cannot be
      detected either way, so --format brotli is the only way in there too.

  stf unpack data.lzma --format lzma -o data.txt
      LZMA1 defines no magic bytes either, the same as brotli — detection
      from a file works only by the `.lzma` extension, and a `.lzma` stream
      arriving on a pipe, with no filename to go by, cannot be detected at
      all, so --format lzma is the only way in there too. Needs a build
      with `--features c-backed` (or `lzma-c` alone); the default pure
      build has no LZMA1 backend yet.


STREAMING TO STDOUT

  curl -s https://example.com/log.gz | stf cat - | grep pattern
      cat decompresses straight to stdout without ever naming an output
      file — the shape for feeding a compressed stream into another tool.

  stf cat data.bin --format gzip
      cat takes --format for the same reason, and --max-ratio to bound a
      decode that would otherwise stream an enormous file to stdout.


STDIN AND STDOUT VIA `-`

  `-` means the stream, wherever a path is expected: stdin for an input,
  stdout for an output.

  cat notes.txt | stf pack - -o notes.txt.gz
      Stdin has no path to derive a name from, so -o is mandatory here;
      leaving it out is a usage error (exit 2).

  cat notes.txt | stf pack - -o - | wc -c
      Both ends can be `-` at once: stdin in, stdout out.


INSPECTING A STREAM WITHOUT DECODING IT

  stf info notes.txt.gz
      Reports the format, the resolved chain, the fidelity "rung", and the
      size when it's known.

  stf info notes.txt.gz --json
      The same report as machine-readable JSON, for scripting.

  A plain file reports `rung: exact` — stf can seek it, so what it reports
  is verified. A pipe (`stf info -`) reports `rung: forward-only` — a
  stream can only be read once, so this is the tool telling you the format
  was inferred from bytes it saw going by, not confirmed by looking back.


WHAT THIS BUILD CAN DO

  stf formats
      Lists the formats compiled into THIS binary, not everything stf will
      ever support. A pure build (the default) has nine rows: gzip, zlib,
      deflate, bzip2, brotli, lz4, snappy, zstd and xz. zstd's row differs by
      which backend compiled in: a build with the `zstd-c` feature (needs a
      C toolchain) shows `yes` in WRITE, using the real `libzstd`; a
      pure-Rust build falls back to `ruzstd` instead, and shows `weak` in
      WRITE — see "USING A WEAK FALLBACK ENCODER" below. Either way the
      format still reads `.zst` unconditionally; only writing it without the
      C backend needs the flag. xz's row does NOT have this shape: both
      backends show `yes` in WRITE, never `weak` — `--features c-backed`
      swaps the pure-Rust `lzma-rust2` backend for the real `liblzma`, which
      is faster (see "COMPRESSING A FILE" above) but not more capable.
      `--features c-backed` adds a TENTH row, `lzma`, that the pure build
      does not have at all yet — LZMA1 has only a C backend so far; its
      pure-Rust counterpart is not implemented yet.


GUARDING AGAINST DECOMPRESSION BOMBS

  stf unpack bomb.gz --max-ratio 100
      A decompression bomb is a small compressed file that expands to an
      enormous one. --max-ratio refuses a decode once output has grown
      past this multiple of the compressed input (default 10000). gzip's
      structural ceiling is roughly 1032:1, so it cannot reach that default
      alone — here the flag mostly guards oversized input, or lets a
      cautious caller set a tighter bound by hand. It earns its keep once
      later phases add codecs and containers that CAN reach 10000:1.


SKIPPING THE DURABILITY FSYNC

  stf pack big.txt --no-sync
      By default, pack and unpack fsync the output before renaming it into
      place, so a crash cannot leave a truncated file under the real name.
      --no-sync trades that guarantee for speed on bulk or scratch work.


USING A WEAK FALLBACK ENCODER

  stf pack big.dat --format zstd --allow-weak-encoder
      A build with no C toolchain writes `.zst` through `ruzstd`, a
      pure-Rust fallback, instead of the reference `libzstd`. The output is
      valid zstd any tool can read, but markedly larger — measured at 3.53x
      on an 11.7 MB corpus where the C backend's default reaches 6.21x
      (files 76% larger) — and slower (969ms against 118ms in that same
      measurement), and it buffers the whole input in memory rather than
      streaming it, unsuitable for large files. pack refuses such an
      encoder unless this flag is given; run `stf formats` to see which
      codecs in THIS build are affected (WRITE shows `weak` rather than
      `yes`). Rebuild with `--features c-backed` to remove the limitation.
      xz does not have this shape: its pure-Rust backend (`lzma-rust2`) is a
      full codec at ratio parity with `liblzma`, not a weaker fallback, so
      `--allow-weak-encoder` never applies to it, in any build. LZMA1 does
      not have this shape either, for a different reason: its only backend
      so far is the real `liblzma` (via `--features c-backed` or `lzma-c`
      alone) — there is no pure-Rust LZMA1 backend yet for it to fall back
      to, weakly or otherwise. `c-backed` remains a speed choice for xz, not
      a capability one.


EXIT CODES

  0  success
  1  general failure (i/o error, or anything not listed below)
  2  usage error (bad flag, missing -o, existing output without --force)
  3  format not available in this build
  4  fidelity degraded under strict mode
  5  archive or stream is corrupt
  6  resource limit exceeded (e.g. --max-ratio tripped)
  7  unsafe path refused


NOT YET

  A pure build (the default) has nine codecs: gzip, zlib, deflate, bzip2,
  brotli, lz4, snappy, zstd and xz. zstd's pure backend (`ruzstd`) is a weak
  fallback (see "USING A WEAK FALLBACK ENCODER" above); xz's pure backend
  (`lzma-rust2`) is not — it reads and writes full-ratio xz with no C
  toolchain, just slower than `--features c-backed`'s `liblzma` (roughly
  1.2-1.3x to encode, 2-2.2x to decode, measured on a 6.5 MB payload).
  `--features c-backed` upgrades both: zstd to the real `libzstd`, and xz to
  `liblzma` for speed. `--features c-backed` (or `lzma-c` alone) also adds a
  tenth codec, `lzma` — LZMA1, the older format xz superseded — via the real
  `liblzma`; it defines no magic bytes, so it is reachable only through
  `--format lzma`, never by detection. LZMA1's pure-Rust backend does not
  exist yet, so the default pure build has no `lzma` row at all. No archive
  containers (tar, zip, ...) exist yet — Phase 2. `stf formats` always tells
  you the truth about the build you are actually running, whatever this
  page says.
