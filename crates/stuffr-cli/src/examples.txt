stuffr — worked examples

Everything below runs against this build as shown. `stuffr <command> --help`
lists the full flag reference for any one command.


COMPRESSING A FILE

  stuffr pack notes.txt
      Writes notes.txt.gz beside it. The input, notes.txt, is left alone —
      unlike gzip(1), stuffr never deletes or replaces what you compressed.

  stuffr pack notes.txt -o archive.gz
      Choose the output name with -o/--output. Without it, the default is
      the input path plus the chosen format's extension (".gz" today).

  stuffr pack notes.txt --format gzip -o out.bin
      --format names the codec explicitly instead of inferring one from -o's
      extension. Every build — even one with no C toolchain — accepts
      gzip, zlib, deflate, bzip2, brotli, lz4, snappy, zstd, xz, lzma and
      lzip.

  stuffr pack notes.txt --format xz -o out.xz
      A default build writes xz through `lzma-rust2`, a pure-Rust port of
      Tukaani's "XZ for Java" — no C toolchain needed, and unlike zstd's
      pure fallback this is a FULL codec, not a weaker one:
      `--allow-weak-encoder` is never required for xz. Measured on a 6.5 MB
      payload against `--features c-backed`'s real `liblzma`: output sizes
      within 0.02% of each other (parity, not a discount), encoding takes
      roughly 1.2-1.3x as long, and decoding roughly 2-2.2x as long. Both
      backends select CRC64 as xz's integrity check unconditionally, and
      every position in a corruption sweep against either backend's own
      output was detected. `c-backed` is a speed choice for xz, not a
      capability one.

  stuffr pack notes.txt --format lzma -o out.lzma
      LZMA1, the older "alone" format xz superseded. Every build reads and
      writes it, including one with no C toolchain: `--features c-backed`
      swaps the pure-Rust `lzma-rust2` backend for the real `liblzma`,
      which is faster. The two match byte-for-byte on small ordinary
      payloads, but that is not a guarantee across every preset: measured
      on a real file at presets 0/3/6/9, only preset 3 came out identical;
      the rest differ by roughly 0.02-1.4% in size, parity rather than
      identity. Unlike every other codec on this page, `.lzma` defines
      NO magic bytes at all: its header's first byte encodes lc/lp/pb and
      the next four the dictionary size, not a fixed signature, so this
      format can never be detected from bytes alone, on a file or a pipe —
      see "DECOMPRESSING" below. It also has no concatenation convention
      the way gzip and xz do: unlike carrying a checksum, corruption is
      still detected almost everywhere despite that (measured at 4,166 of
      4,170 swept byte positions) through the LZMA range coder's own
      structural sensitivity, not a designed check.

  stuffr pack notes.txt --format lzip -o out.lz
      LZIP, a newer container around the same LZMA1 payload `lzma` above
      wraps, with two differences that matter: it carries a 4-byte `"LZIP"`
      magic (so, unlike `.lzma`, a `.lz` file IS detected automatically —
      see "DECOMPRESSING" below), and it defines a real multi-member
      concatenation convention with a mandatory CRC32/size trailer per
      member, so `cat a.lz b.lz | stuffr cat --format lzip -` decodes both
      members' data, not just the first. Only one backend exists for it —
      the same pure-Rust `lzma-rust2` xz and lzma use — so `--features
      c-backed` makes no difference to this row at all, unlike zstd's or
      xz's. Validated directly against the reference `lzip` 1.26 tool in
      both directions, including the two-member case.

  stuffr pack notes.txt --level 9
      --level asks the codec for a tradeoff: gzip accepts 0 (fastest,
      largest output) through 9 (slowest, smallest output). xz's range is
      the same shape, 0-9, with 6 as its default too, and lzma and lzip
      share that exact range too — both wrap an LZMA1 payload under the
      hood. bzip2's range is 1-9, not 0-9 — it has no "store" level, so
      --level 0 is a usage error (exit 2) rather than meaning "don't
      compress". brotli's range is 0-11, and unlike every other codec here
      its OWN default is 11 (the slowest setting it has), not something in
      the middle of the range. zstd's range is the widest and the only one
      with negative numbers — -131072 through 22 on this build — where
      negative levels are zstd's "fast" modes, faster than level 1 at the
      cost of ratio; its default is 3. lz4 and snappy have no level at all —
      neither underlying crate exposes such a knob — so --level is accepted
      and silently ignored rather than rejected, unlike every other codec on
      this page.

  stuffr pack notes.txt --force
      Without --force, pack refuses to overwrite an existing output: exit
      code 2, the existing file left untouched, nothing written.


DECOMPRESSING

  stuffr unpack notes.txt.gz
      Writes notes.txt, stripping the recognised extension. As with pack,
      an existing destination is refused unless --force is given too.

  stuffr unpack notes.txt.gz -o out.txt --force
      Choose the name and allow overwriting an existing one.

  stuffr unpack data.bin --format gzip -o data.txt
      --format names the codec explicitly instead of detecting it. Some
      formats carry no magic bytes and no conventional extension, so an
      explicit --format is the only way to reach them.

  stuffr unpack raw.bin --format deflate -o data.txt
      Raw deflate has no header, no trailer and no conventional extension,
      so it cannot be detected at all — --format is the ONLY way in.

  stuffr unpack data.br --format brotli -o data.txt
      brotli defines no magic bytes at all, unlike gzip/zlib/bzip2's header
      bytes — detection from a file works only by the `.br` extension. A
      brotli stream arriving on a pipe, with no filename to go by, cannot be
      detected either way, so --format brotli is the only way in there too.

  stuffr unpack data.lzma --format lzma -o data.txt
      LZMA1 defines no magic bytes either, the same as brotli — detection
      from a file works only by the `.lzma` extension, and a `.lzma` stream
      arriving on a pipe, with no filename to go by, cannot be detected at
      all, so --format lzma is the only way in there too. No special build
      is needed — every build has an LZMA1 backend.

  stuffr unpack data.lz
      LZIP, unlike its older sibling LZMA1 just above, DOES carry a 4-byte
      `"LZIP"` magic at offset 0 — so this is detected automatically, on a
      file or a pipe, and needs no --format at all.


STREAMING TO STDOUT

  curl -s https://example.com/log.gz | stuffr cat - | grep pattern
      cat decompresses straight to stdout without ever naming an output
      file — the shape for feeding a compressed stream into another tool.

  stuffr cat data.bin --format gzip
      cat takes --format for the same reason, and --max-ratio to bound a
      decode that would otherwise stream an enormous file to stdout.


STDIN AND STDOUT VIA `-`

  `-` means the stream, wherever a path is expected: stdin for an input,
  stdout for an output.

  cat notes.txt | stuffr pack - -o notes.txt.gz
      Stdin has no path to derive a name from, so -o is mandatory here;
      leaving it out is a usage error (exit 2).

  cat notes.txt | stuffr pack - -o - | wc -c
      Both ends can be `-` at once: stdin in, stdout out.


INSPECTING A STREAM WITHOUT DECODING IT

  stuffr info notes.txt.gz
      Reports the format, the resolved chain, the fidelity "rung", and the
      size when it's known.

  stuffr info notes.txt.gz --json
      The same report as machine-readable JSON, for scripting.

  A plain file reports `rung: exact` — stuffr can seek it, so what it reports
  is verified. A pipe (`stuffr info -`) reports `rung: forward-only` — a
  stream can only be read once, so this is the tool telling you the format
  was inferred from bytes it saw going by, not confirmed by looking back.


WHAT THIS BUILD CAN DO

  stuffr formats
      Lists the formats compiled into THIS binary, not everything stuffr will
      ever support. A pure build (the default) has eleven rows: gzip, zlib,
      deflate, bzip2, brotli, lz4, snappy, zstd, xz, lzma and lzip. zstd's
      row differs by which backend compiled in: a build with the `zstd-c`
      feature (needs a C toolchain) shows `yes` in WRITE, using the real
      `libzstd`; a pure-Rust build falls back to `ruzstd` instead, and shows
      `weak` in WRITE — see "USING A WEAK FALLBACK ENCODER" below. Either
      way the format still reads `.zst` unconditionally; only writing it
      without the C backend needs the flag. xz's and lzma's rows do NOT have
      this shape: both backends show `yes` in WRITE, never `weak` —
      `--features c-backed` swaps the pure-Rust `lzma-rust2` backend for the
      real `liblzma`, which is faster (see "COMPRESSING A FILE" above) but
      not more capable. lzip's row is unaffected by `c-backed` entirely — it
      has only ever had the one, pure-Rust `lzma-rust2` backend, so this
      feature changes nothing about it, in either direction. All three
      tiers (`pure`, `pure` plus `c-backed`, and any granular combination)
      list all eleven formats — the ONLY capability difference the
      `c-backed` feature makes anywhere in this matrix is zstd's WRITE
      column, `weak` against `yes`.

      The PARALLEL column is truthful per build too, and independent of
      the WRITE column above: on the default (`pure`) tier it reads `yes`
      for `xz` and `lzip` and `-` for every other format, including
      `zstd` — `ruzstd` has no multi-threaded encoder to hand a worker
      count to. Adding `--features c-backed` flips `zstd` to `yes` as
      well, alongside its WRITE column becoming `yes`; it changes nothing
      else in this column, on any tier.


GUARDING AGAINST DECOMPRESSION BOMBS

  stuffr unpack bomb.gz --max-ratio 100
      A decompression bomb is a small compressed file that expands to an
      enormous one. --max-ratio refuses a decode once output has grown
      past this multiple of the compressed input (default 10000). gzip's
      structural ceiling is roughly 1032:1, so it cannot reach that default
      alone — here the flag mostly guards oversized input, or lets a
      cautious caller set a tighter bound by hand. It earns its keep once
      later phases add codecs and containers that CAN reach 10000:1.


SKIPPING THE DURABILITY FSYNC

  stuffr pack big.txt --no-sync
      By default, pack and unpack fsync the output before renaming it into
      place, so a crash cannot leave a truncated file under the real name.
      --no-sync trades that guarantee for speed on bulk or scratch work.


USING A WEAK FALLBACK ENCODER

  stuffr pack big.dat --format zstd --allow-weak-encoder
      A build with no C toolchain writes `.zst` through `ruzstd`, a
      pure-Rust fallback, instead of the reference `libzstd`. The output is
      valid zstd any tool can read, but markedly larger — measured at 3.53x
      on an 11.7 MB corpus where the C backend's default reaches 6.21x
      (files 76% larger) — and slower (969ms against 118ms in that same
      measurement), and it buffers the whole input in memory rather than
      streaming it, unsuitable for large files. pack refuses such an
      encoder unless this flag is given; run `stuffr formats` to see which
      codecs in THIS build are affected (WRITE shows `weak` rather than
      `yes`). Rebuild with `--features c-backed` to remove the limitation.
      xz does not have this shape: its pure-Rust backend (`lzma-rust2`) is a
      full codec at ratio parity with `liblzma`, not a weaker fallback, so
      `--allow-weak-encoder` never applies to it, in any build. lzma (the
      older LZMA1 "alone" format) shares xz's shape now too: its pure-Rust
      backend is the same full-ratio `lzma-rust2`, so `--features c-backed`
      is purely a speed choice for it as well, never a capability one.
      lzip does not have this shape either, for a simpler reason still: it
      has exactly one backend, period — there is no second, C-backed
      implementation for it to differ from, weakly or otherwise, so
      `--features c-backed` changes nothing about its row at all.


PARALLEL ENCODE FLAGS

  stuffr pack big.dat --format xz --threads 4
      Encode with 4 worker threads instead of stuffr's default of one. Only
      THREE of this build's eleven formats actually parallelise their
      encoder: xz and lzip on every build, and zstd only with --features
      c-backed (the default ruzstd encoder has no multi-threaded path).
      Counted by implementation rather than format this is four
      (zstd-c, xz-c, xz-pure, lzip), because xz has two interchangeable
      backends — but xz-c and xz-pure register the same format and never
      both compile in, so no single build ever shows more than three
      PARALLEL rows in `stuffr formats`. The other eight (nine counting only
      one xz backend) accept --threads without error but encode
      single-threaded regardless, since their crates expose no MT encoder
      to hand a worker count to. --threads is deliberately opt-in rather
      than auto-detected: a multi-threaded encoder splits its input across
      workers, so the very same file compresses to different bytes
      depending on how many workers ran. Omitting --threads (and --turbo,
      and leaving STUFFR_THREADS unset) keeps pack single-threaded, so a
      given input, given the same flags and the same environment, always
      produces the same output bytes — "same machine" is not part of the
      promise once --threads 0 is in play, because auto-detection
      resolves against cgroup CPU quotas, not just core count.
      --memory-limit does not affect this: it bounds allocation and the
      worker count the governor can grant, never which bytes a worker
      count already granted produces. Passing --threads 0 asks stuffr to
      auto-detect a worker count
      instead, trading that byte-for-byte reproducibility for speed.
      --threads exists only on pack; multi-threaded decode is out of scope
      for this phase, and unpack/cat refuse the flag outright rather than
      silently accepting and ignoring it — see
      "threads_is_not_offered_on_decode_subcommands" if you want the
      enforcement in test form.

  stuffr pack big.dat --format xz --threads 4 --turbo
      --turbo lifts the CPU cap only, letting stuffr use the full detected
      core budget instead of a conservative default worker count.
      --memory-limit (below) still binds regardless of --turbo: turbo
      means "use my cores," not "ignore the OOM killer."

  stuffr pack big.dat --format xz --memory-limit 512M
  stuffr unpack archive.xz --memory-limit 512M
      --memory-limit caps the memory stuffr will ask for. It accepts a plain
      byte count or a binary, 1024-based K/M/G suffix (e.g. 512M or 2G) —
      matching what `xz --memlimit` and every other tool in this space
      mean by "M", not the decimal 1000-based reading. A malformed value
      (512MB, a decimal unit, anything else this parser doesn't recognise)
      is a usage error naming the accepted forms, never a silent fall back
      to the default — a user who typed 512MB and got 25% of RAM instead
      would have no way to notice. On pack this bounds the worker count;
      unpack, cat and info accept it too, since a decode can also need to
      fit inside a memory ceiling even with no threads to bound. Defaults
      to 25% of available RAM, honouring cgroup limits; `stuffr info` reports
      the resolved figure, humanized (e.g. "256 MiB"), on every build.

      The bound has teeth: xz and lzip cost roughly 128 MiB per worker
      below preset 7 and roughly 896 MiB per worker at preset 7 and above
      (the match finder, not the block buffer, dominates). On the 256 MiB
      floor this build defaults to when it cannot read available memory
      (macOS, with no /proc/meminfo), that means `stuffr pack big.dat --format
      xz --threads 8 --level 9` silently runs with exactly ONE worker —
      the governor protecting the machine, not a bug — unless
      --memory-limit is raised. A 4 GiB budget gets 4 workers at that same
      level, or 32 (then CPU-capped) at the default level 6.

  --threads, --turbo and --memory-limit build the thread governor that
  pack's encode path consumes: --threads and --turbo resolve to a worker
  count via the same precedence STUFFR_THREADS and a future config file will
  follow, and --memory-limit resolves to the byte cap that count is
  clamped against — divided by the codec's own measured per-worker demand,
  never a flat division. Omitting --threads builds no governor at all —
  the codec sees no worker count and encodes single-threaded, which is
  what keeps output byte-reproducible by default. unpack, cat and info
  accept --memory-limit and validate it the same way. info only reports
  the resolved figure (it never decodes), but unpack and cat pass it
  through to the decoder: a handful of pure codecs size a dictionary
  buffer from a value the file declares in its own header, before
  producing any output, so an unbounded decode of a hostile file can
  allocate far more than the archive's own size would suggest — this is
  what closed the xz-pure/lzip/lzma-pure decode denial-of-service, each
  refusing at exit 6 (see "EXIT CODES" below) naming the declared size,
  the limit and the flag, never the exit 5 a genuinely corrupt archive
  gets. Omitting the flag on unpack/cat still binds — it resolves to the same
  25%-of-RAM default as pack — because a bound that defaults off closes
  nothing.


EXIT CODES

  0  success
  1  general failure (i/o error, or anything not listed below)
  2  usage error (bad flag, missing -o, existing output without --force)
  3  format not available in this build
  4  fidelity degraded under strict mode
  5  archive or stream is corrupt
  6  resource limit exceeded (e.g. --max-ratio or --memory-limit tripped)
  7  unsafe path refused


NOT YET

  A pure build (the default) has eleven codecs: gzip, zlib, deflate, bzip2,
  brotli, lz4, snappy, zstd, xz, lzma and lzip. zstd's pure backend
  (`ruzstd`) is a weak fallback (see "USING A WEAK FALLBACK ENCODER" above);
  xz's and lzma's pure backends are not — both read and write full-ratio
  output with no C toolchain, just slower than `--features c-backed`'s
  `liblzma` (roughly 1.2-1.3x to encode, 2-2.2x to decode, measured on a
  6.5 MB payload). `--features c-backed` upgrades all three: zstd to the
  real `libzstd`, and xz/lzma to `liblzma` for speed. lzip has no such
  upgrade path at all — it has exactly one backend (the same pure-Rust
  `lzma-rust2` xz and lzma use), so `--features c-backed` changes nothing
  about it, and there is no weak-fallback distinction for it either. No
  archive containers (tar, zip, ...) exist yet — Phase 2. `stuffr formats`
  always tells you the truth about the build you are actually running,
  whatever this page says.
